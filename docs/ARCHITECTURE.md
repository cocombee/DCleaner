Runtime epochs: `optimizer_storage::epoch::RuntimeOwner` is the production entry to protected storage. For a predecessor, its provenance stays intact until request Running rows and intent CommitStarted rows have separately committed to Uncertain. The startup review flag is a snapshot of pending/uncertain work, not service/helper readiness. Seven native fixture cases cover these admission/restart paths (the PID-reuse classifier uses an explicitly synthetic old creation time); two journal fixtures cover matching-state isolation and failed-COMMIT preservation. Production LocalSystem/SCM integration, independent native post-state recovery and resource lease release remain open.

## Decision ADR-001 — Accepted: fully native Rust

Launch-freeze hardening history, 16 October 2026: the user reported an approximately 30-second screen stall when opening the installed OpenGL build. The first mitigation used WGPU/Direct3D 12 with explicit CPU-adapter selection (Windows WARP), FIFO presentation and at most one queued frame. Later high-DPI measurements exposed the CPU renderer's own cost; the current installed policy selects supported acceleration by default, with explicit `--software-rendering` recovery and no OpenGL fallback. macOS keeps the platform WGPU selection and remains runtime-unverified. `src/render_config.rs` owns this policy. The original stall's cause and normal-window resolution remain unproven; this is not evidence that the GPU driver was faulty.

`src/startup_load.rs` performs initial preference/history/Custom Clean settings/category reads in a worker. `App::construct` no longer performs those profile/filesystem reads. Until completion, the command worker/readability guards keep actions disabled; the UI can paint loading state. The saved appearance/landing page is applied only after the worker result arrives. A missing startup root or disconnected reader remains blocked with Retry startup rather than authorizing effects against the current directory. The read-only `--startup-readiness-json` diagnostic exits before instance activation, native window creation or graphics setup. Fixture renders are still separate from native surface/present and desktop-stability acceptance.

The user requires all application UI and logic in Rust. egui/eframe renders native desktop windows; one Rust application service coordinates workers and platform operations. React/Electron and Tauri were superseded before delivery. Their temporary prototype remains outside the repository.

Alternatives: Tauri preserves HTML/CSS components but includes a JavaScript/webview UI, conflicting with the accepted requirement. Flutter is not Rust. Native Rust requires reproducing the accepted screenshot composition through shared painted controls and inspecting the native output.

Consequences: shared core contracts across Windows/macOS; native builds on each OS; platform permissions, Trash behaviour, signing and installation remain OS-specific. Local cleaning needs no server. Cloud cleaning and independent update catalogues require authenticated external providers and capability setup.

## Commands and transitions

Cloud metadata is a separate observation owner: provider, immutable account subject and explicit storage visibility bind every page/cursor. The coordinator checks current scope before and after each page, bounds retained metadata and pagination, preserves partial results, and never treats a failed/incomplete source as empty or authoritative. Google Drive's first adapter queries only API-visible untrashed Drive items; it does not prove that a token can see the entire account. Provider hashes identify possible duplicate groups, not verified equality, unused status or permission to remove anything. Gmail sizes must remain estimates. No inventory snapshot authorizes a remote mutation.

Cloud scans have a default five-minute elapsed-time budget, checked before and after provider calls and during row acceptance; late page data cannot turn expiry into success. Expiry preserves previously accepted rows as partial, or fails explicitly if no rows were accepted. A blocking call may overrun the budget until it returns. Every future provider adapter must also bound decoding before allocating its returned page. Complete means that the bounded query's pagination ended without a known gap, not an atomic remote snapshot or complete visibility of an entire account. Configurable/resumable traversal for accounts beyond the first bounded scan remains required before full workflow acceptance.

Cloud HTTP requests use fixed provider endpoints, native TLS validation, no redirects/proxies/automatic retries, bounded bodies and deadlines checked before/after blocking reads. Cancellation cannot interrupt a blocking library call until it returns. Access tokens have no raw secret getter and their owned source buffer is zeroized on drop; transport-internal copies are not claimed to be scrubbed. The integrated source adds four provider adapters, DCleaner-owned client setup, PKCE consent, client-bound refresh, Windows DPAPI/macOS Keychain persistence, account switching and native cloud views. No provider registrations have been supplied, so setup must remain explicit and no connection may be fabricated. OneDrive enumerates existing drives and requires a choice when more than one exists; it never calls the auto-provisioning `/me/drive` route.

Cloud effects use a separate fixed-route owner. Reviewed scan IDs, account generation, exact subject/storage, provider revisions and fresh metadata checks precede one explicit trash/restore request. SQLite reserves a synced intent before dispatch and records confirmed, failed or uncertain outcomes through a terminal compare-and-set. A worker ending without a durable receipt leaves an uncertain intent; no automatic replay occurs. History keeps provider restore metadata after local sign-out. Provider APIs differ: a preflight cannot close every concurrent-change race, Gmail trash does not release quota immediately, OneDrive work/school restore is unsupported by the documented Personal restore API, and folders require descendant-aware review. These limitations must remain visible; they are not full parity acceptance. No permanent-delete endpoint exists.

## Persistence and recovery

Selected optimizer images have a separate read-only identity owner. A Windows handle excludes ordinary write/delete sharing while the reader retains volume/file identity, size, timestamps, attributes, hard-link count, normalized final path, header fields and a complete SHA-256. The header is compared against the bytes read during hashing. Image/header reads have finite byte bounds and observe cancellation between calls; synchronous filesystem calls have no wall-clock guarantee. Fresh revalidation rejects any retained observation change, including a replacement file with identical bytes. A snapshot reserves nothing after return, proves neither executable signature nor component ownership, and is not a complete Windows loader validation. Parent path redirection is reported through the resolved path rather than silently certified as absent. An eventual effect owner must independently establish associations, authority, current state and recovery. The non-Windows adapter reports unsupported. This owner is not yet wired to a GUI optimizer action.

Performance Optimizer's [static reconstruction contract](design/evidence/performance-optimizer-contract.json) now separates observed UI/native facts from the proposed DCleaner service. The crate-private Windows pipe adapter now provides serial overlapped connect/read/write under one absolute exchange deadline. It checks cancellation/deadline before submission and after completion, ends the exchange on errors, distinguishes broken-pipe EOF from zero-byte non-progress reads and never flushes through blocking FlushFileBuffers.
