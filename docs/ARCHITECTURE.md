# DCleaner architecture

## Decision ADR-001 — Accepted: fully native Rust

The user requires all application UI and logic in Rust. egui/eframe renders native desktop windows; one Rust application service coordinates workers and platform operations. React/Electron and Tauri were superseded before delivery. Their temporary prototype remains outside the repository.

Alternatives: Tauri preserves HTML/CSS components but includes a JavaScript/webview UI, conflicting with the accepted requirement. Flutter is not Rust. Native Rust requires reproducing the accepted screenshot composition through shared painted controls and inspecting the native output.

Consequences: shared core contracts across Windows/macOS; native builds on each OS; platform permissions, Trash behaviour, signing and installation remain OS-specific. Local cleaning needs no server. Cloud cleaning and independent update catalogues require authenticated external providers and capability setup.

The UI sends typed Rust commands directly to the application service. Scan results carry opaque UUIDs and immutable file metadata. The cleanup service resolves IDs from the current analysis and never accepts caller-supplied deletion paths. Worker completion is observed via a bounded/single-operation channel; no second authoritative database model lives in the UI.

## Commands and transitions

`Idle -> Scanning -> ReviewedAnalysis | CancelledAnalysis | Failed`.
`ReviewedAnalysis -> Confirming -> Cleaning -> Completed | PartiallyCompleted | Interrupted`.
`Idle -> FolderAnalysis -> ReadOnlyResults | Cancelled | Failed`.

An active operation rejects another operation. Changing cleaning settings invalidates the old analysis. Cancelled analyses cannot authorize cleanup. Cleanup success counts only completed Trash calls whose receipt was durably written; uncertain operations are separated on restart. The UI does not infer success from elapsed time, progress, file absence or a selected checkbox.

Each row owns its real supported controls: details/review/more, selected-ID changes, reversible startup state or update request. The pinned footer summarizes the same state; it is not the only route to per-row actions. An unsupported effect exposes its exact limitation and stays an open parity obligation.

Startup state belongs to Windows, including changes made by other tools. User and common Startup folders resolve their own StartupApproved hives (HKCU and HKLM respectively); inventory, preflight, effect and restoration must use the same source identity. Returning to the foreground and periodic visible-page refresh re-read state, preserving selection by stable identity. Never overwrite externally disabled state with a UI default or infer Enabled from a failed source read.

Browser privacy uses known profile roots and actual supported database schemas. Scan projections contain category/site metadata without cookie secrets. Cleanup resolves current opaque record IDs, applies persistent cookie keep rules, checks browser conflicts, snapshots and syncs recovery material, then uses a transaction. Restore is a separate reviewed effect: only the exact unchanged post-cleanup database may be replaced from its validated snapshot while the browser is closed. A changed database or uncertain journal blocks restoration; backups are preserved and no interrupted effect is replayed automatically.

Driver state separates installed metadata, native property-read failures and exact WUA offers. A missing offer is not proof that a driver is current; WUA does not supply a candidate driver version through the used interface. Ambiguous device/offer matching blocks an update intent. Reviewed update order is exact preflight, synced intent, restore point, verified signed installed-package export, fresh preflight, exact WUA download/install, aggregate and per-item status, reboot classification and actual device verification. Restore has its own exact backup/device identity and journal. Batch offers deduplicate update GUID/revision/source, stop on failure/uncertainty/pending restart, and state that a shared offer's verification covers its representative device rather than all grouped devices. Native install/restore cancellation and post-reboot verification remain open; Windows is never restarted automatically.

The non-Windows adapter implements the same driver action boundary so the shared UI compiles on macOS, but returns `NativeUpdateBoundaryUnavailable` at its first native read and every effect entry point. Reviewed update/restore calls therefore fail before creating an operation journal. Native Windows x64 and Apple Silicon CI builds verify the shared contracts and fixture tests; this does not provide a Mac driver-update capability or installed UI evidence.

Health Check starts from the accepted finding-card landing view. Only Start Health Check begins browser/cookie prerequisites; app launch does not itself request browser closure. Each step owns scanning, browser conflict review, current finding selection, exact action review, cancellation, partial/failed results, skip/advance and final summary. Cookie-rule errors block Privacy rather than unrelated Space/Resolve Issues scans. The Health coordinator resolves service-owned IDs into plans and consumes typed receipts. Native owner calls that cannot be interrupted observe cancellation only after return. Startup inventory does not classify an app as unnecessary; Driver Updater and background optimization are not yet included in this Health scan. Those gaps remain explicit rather than inferred from dedicated-section availability.

Recycle Bin is a separate effect owner from filesystem Trash moves. Inventory exposes scan-local UUIDs and shell metadata; callers cannot supply deletion paths or native tokens. Restore and permanent purge require a complete reviewed inventory, readable journal, fresh identity/metadata comparison and durable per-item intent. Purge has an additional irreversible-action acknowledgement. Failed post-effect observation remains uncertain, and no automatic retry follows restart. Folder entry counts are never represented as bytes; the underlying shell enumeration is non-cancellable until its first native call returns.

## Persistence and recovery

Selected optimizer images have a separate read-only identity owner. A Windows handle excludes ordinary write/delete sharing while the reader retains volume/file identity, size, timestamps, attributes, hard-link count, normalized final path, header fields and a complete SHA-256. The header is compared against the bytes read during hashing. Image/header reads have finite byte bounds and observe cancellation between calls; synchronous filesystem calls have no wall-clock guarantee. Fresh revalidation rejects any retained observation change, including a replacement file with identical bytes. A snapshot reserves nothing after return, proves neither executable signature nor component ownership, and is not a complete Windows loader validation. Parent path redirection is reported through the resolved path rather than silently certified as absent. An eventual effect owner must independently establish associations, authority, current state and recovery. The non-Windows adapter reports unsupported. This owner is not yet wired to a GUI optimizer action.

Performance Optimizer's [static reconstruction contract](design/evidence/performance-optimizer-contract.json) now separates observed UI/native facts from the proposed DCleaner service. The original UI groups found/deactivating as Active, deactivated/activating as Sleeping and ignored as Excluded. Details expose associated service, task, autostart, registry and packaged-app entries, including temporarily enabled entries and state managed by another optimizer. These cannot be reduced to one startup switch or a process-kill operation.

Nine decompiled functions in the pinned CCleanerReactivator helper establish an executable-scoped re-enable RPC, IFEO debugger checks and registration management, full-path filter fields, recursion protection and child-process launch orchestration. They do not establish the service-side sleep mutations, impact classifier or return-to-sleep implementation. The helper's finite input-idle wait is not proof that it watches the app until exit. Those are required investigations before claiming native parity.

Supplementary bounded offline inspection links 15 service command registrations to callback tables. Type metadata, a constructor table store and adjustment forwarding code now link five interface slots to concrete module implementations; the two re-enable names share the `exeName` callback and lead to the same module path. Underlying manager/component mutation, runtime dispatch, lifecycle and recovery remain unresolved. The focused REA provider timed out at startup. A separate headless Ghidra fallback successfully decompiled five selected service procedures using the Windows ABI, with no target execution. One selection follows 66 p-code instruction addresses beyond its requested PE range despite explicit body assignment; its boundary or tail-transfer semantics remain unresolved. These static summaries establish neither complete service coverage nor runtime effects, and carry no canonical REA Evidence IDs.

The next bounded pass resolves the request pipeline across 23 selected procedures, including three helpers with metadata-linked unwind fragments. Producers coalesce or enqueue requests, signal a work event, and a worker dequeues them before calling a dispatcher. The re-enable wait is bounded at 8,000 ms; handle signaling and returned request status remain separate from verified component post-state. Provider virtual mutation targets and the stored re-enable callable remain unresolved. DCleaner's background owner must preserve distinct queued, running, timed-out, partial and verified outcomes, with explicit waiter ownership when requests coalesce. A worker result alone cannot authorize a Sleeping receipt or a restoration claim.

The selected constructor path now statically links the worker's held pointer/owner pair to CProgramManager. Setup installs the pair at primary-this+0x90/+0x98; the worker reads it through secondary-this+0x88/+0x90 and subtracts eight before dispatch. This establishes that path's receiver provenance, while later rebinding, other paths and runtime dispatch remain open. Separate bounded decoding covers the two provider dependencies, including the callee containing all 230 addresses that followed the original prelude's range. Constructor/destructor decompiler samples outside their selected ranges remain unreviewed.

Four initial service procedures have populated canonical REA dossiers under isolated, hash-pinned launcher corrections and explicit function/code seeds. The installed launcher and global configuration remain unchanged. Only the Subroutine References analyzer remains enabled; actual direct-call-site seeds repair the loader's one-byte placeholders. Three diagnostic placeholder records are excluded. The transition routine retains 1,086 assembly lines/167 CFG blocks but its 3,000-operation value-flow facet is truncated. Numeric states and actual component post-state are not inferred. The deactivation-route helper delegates to entry, debugger, property and persistence owners. This is selected static coverage, not complete service analysis or verified Sleep/Wake effects.

Twenty-four further canonical dossiers trace those delegates. Twenty-two have retained facets entirely inside their selected PE unwind scopes, including a writer and a query helper with metadata-linked fragments. The entry-loop and comparator dossiers each follow a trailing padding INT3 beyond their bounds; those instructions, crossing CFG blocks and 37/11 value-flow operations respectively are excluded from semantic claims. The in-scope loop applies shared-entry and status checks, collects entries and dispatches a later action. The association predicate checks other associated keys against modification-record presence; that presence alone is not a verified native Sleeping state. Source-bound SQL confirms read, update, insert, insert-or-update and delete routes for modification data, without proving their runtime results or opaque payload grammar. The debugger path prepares Debugger, FilterFullPath and UseFilter, and its writer reaches RegCreateKeyExW/RegSetValueExW/RegCloseKey. Wrapper failures do not all stop subsequent writes, and the filtered wrapper contains no read-back verification.

Cleanup/query leaves now reach value/key deletion and enumeration APIs. The recursive helper can replace an enumeration error with a delete result, and one precheck treats a missing key as success. The Debugger cleanup gate depends on an incompletely interpreted comparator; another wrapper has an assembly/value-flow argument discrepancy. A separate reported-count gate checks zero subkeys and zero values, while the selected operation remains delegated. None of these gates proves ownership or restoration. A bounded return-check helper preserves RAX/AL on its successful RET path; observed numeric status bytes still do not certify effects. DCleaner's independent shared-resource owner must retain exact associations, fresh native observations and its own recoverable changes. Cleanup ownership, concrete non-registry mutations, complete discovery, return-to-sleep and runtime post-state evidence remain open.

Closed read-only optimizer database snapshots establish separate app/entry and component/subcomponent mapping tables, executable/ignore registrations and program/entry modification records. No foreign keys are declared, and the examined modification payload grammar remains opaque. DCleaner's own typed identities, durable intents, verified outcomes and explicit lease ownership must remain authoritative; a vendor table name or opaque record must not become an inferred effect or recovery receipt. Snapshot schema/aggregate evidence came from Python; REA SQLite reads failed at the filesystem boundary and are not counted as completed REA inspection.

The IFEO preflight owner keeps raw registry type/data, unrelated values and direct filter observations. Missing, denied, malformed, limited, cancelled and failed reads stay distinct. Windows 7 and later expose this IFEO key as [shared across registry views](https://learn.microsoft.com/en-us/windows/win32/winprog64/shared-registry-keys); requested 32/64 views are observations rather than two independent registrations. Syntax validation of a supplied path is not verified executable identity, and sequential reads are not an atomic snapshot. An effect owner must obtain fresh state and reject interference before any future write. This module performs no such writes and is not connected as a Sleep action.

DCleaner must implement an independent background lease owner whose lifecycle survives the GUI. Its proposed flow is current app/component inventory, exact reviewed resource set, verified helper/service readiness, durable before/after intent, application of supported component changes, post-state verification, temporary activation on app launch and verified return-to-sleep or explicit restoration. Full executable identity and component snapshots are authority; filenames and publisher/display-name matches alone are insufficient. Unknown association, unsupported component kinds, foreign ownership or changed native state must remain visible and prevent a false Sleeping receipt. Per-app completion, partial outcomes, interrupted recovery and Activate all require exact owned leases rather than unscoped registry cleanup.

Before any launch interception is armed, the helper and service need a verified protocol and authenticated, narrowly scoped requests, a working ordinary-launch fallback, preserved command line/current directory, recursion prevention and journaled recovery. IFEO changes must preserve other debugger registrations and path filters. Helper packaging remains open: an elevated component must use an administrator-protected executable location and must not execute the current user-writable GUI binary. Keep one GUI installation and shortcut; helper mode must not activate that GUI or share its foreground-instance path. Native installation, registration, app launch and effects remain unperformed under the user's inspection boundary. macOS needs its own approved app-lifecycle and background-service design; Windows IFEO is not a cross-platform adapter. This is the implementation contract, not an implemented optimizer capability.

The independent Rust protocol codec now implements 12-byte versioned frames and an 8 KiB JSON payload bound. It accepts readiness requests and owned lease/invocation identifiers, never executable paths, launch commands, registry locations or client-authored native snapshots. Reads distinguish clean disconnects from truncated frames; invalid headers are rejected before payload allocation. Strict schemas reject unknown/duplicate fields, and responses must match exchange ID, response variant and invocation ID. Queue/running/partial/verified outcomes remain distinct data; serializing one does not establish its truth. Seven fixture tests cover fragmented streams, every truncation boundary, oversize/version/direction rejection, schema injection, nil identities, stale/wrong-invocation responses and partial writes. Production channel integration, service-instance pinning, durable request-ledger integration, readiness/fallback and the effect owner remain unimplemented. The internal peer-identity boundary below is separately fixture-tested. This codec is not yet connected to an installed helper, service or optimizer page.

The crate-private Windows pipe adapter now provides serial overlapped connect/read/write under one absolute exchange deadline. It checks cancellation/deadline before submission and after completion, ends the exchange on errors, distinguishes broken-pipe EOF from zero-byte non-progress reads and never flushes through blocking FlushFileBuffers. Targeted cancellation drains the exact native operation before releasing its buffer, boxed OVERLAPPED or manual-reset event; completion can race cancellation, and moved bytes are not delivery or effect receipts. Windows cancellation draining can exceed the deadline, so this is not a hard wall-clock guarantee. Eleven native fixture tests cover protocol exchange, already-connected/pending accepts, read cancellation, blocked-write timeout, deadline reuse prevention, disconnect, pre-cancel/expiry, completed-cancellation races and zero-byte peer writes. Byte-at-a-time writes do not establish a particular native read fragmentation pattern; the separate codec fixtures explicitly enforce fragmentation. These tests use random local endpoints with remote clients rejected; their default fixture ACL is not a production security policy. The independent native identity/descriptor boundary is implemented below. Production application integration still requires service-instance pinning, lease authorization, admission bounds, a durable service lifecycle and protected helper packaging. The adapter creates no production endpoint and installs/registers nothing. Native timing tests and completion-race fixtures do not cover injected wait-handle failures or malicious peer identities. Implementation follows the [ReadFile overlapped requirements](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-readfile) and [CancelIoEx completion-lifetime requirements](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelioex).

The crate-private security boundary fixes the production pipe owner to LocalSystem. Its protected DACL grants SYSTEM explicit full access and the configured client only data read/write, read attributes, READ_CONTROL and SYNCHRONIZE (`0x00120083`), excluding generic write, attribute writes, DACL writes and FILE_CREATE_PIPE_INSTANCE. A normal-user native comparison showed `0x00120003` client opens fail while `0x00120083` works; sandboxed token restrictions independently rejected fixture access, so final native tests use the normal user token without elevation. Client opens use identification-level SQOS, check the owner and exact unordered pair of plain allow ACEs, and reject missing/null/unprotected or broadened ACLs. First-instance, local-only, non-inheritable server binding requires unimpersonated SYSTEM identity. This trusts the SYSTEM boundary rather than cryptographically identifying a specific service binary; protected packaging remains required.

Caller identity is copied from the last-read pipe token as canonical account SID plus Windows session ID, not supplied by a frame. Canonical round-trip validation rejects native SID-parser aliases/overflow spellings. The server rejects an existing thread impersonation context, reads the native token with OpenAsSelf, reverts before returning, and aborts if reverting fails. There is no async dispatch/callback while impersonating. `read_authenticated_request` keeps bounded parsing, peer authentication and the exchange budget on the same PipeIo, returns private-fields caller/request data only after success, and poisons the stream on parser or authentication errors. The eventual service must still resolve lease/invocation ownership from its own durable data. Account/session identity does not distinguish separate logons within one session, does not authenticate an executable, and does not make arbitrary request IDs authoritative.

Eleven native fixture cases cover authenticated-frame-to-ledger binding, principal ownership/canonicalization, exact permission rejection, narrow client opens and production-owner spoof rejection, extra-instance/name collision rejection, actual token/session matching, preserving pre-existing impersonation, malformed/unauthorized request rejection, SYSTEM bind admission and bounded connect cancellation/busy waits. The fixture owner override is private to cfg(test); current-user tests cannot demonstrate isolation from an attacker who owns and can alter that test object. No SYSTEM service, registered helper, privileged native effect or live visual acceptance is established. Relevant primary contracts are [named-pipe access rights](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights), [OpenThreadToken at identification level](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-openthreadtoken) and [RevertToSelf failure handling](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-reverttoself).

The internal invocation ledger accepts production admission only through an authenticated Reactivate request with its exact lease/invocation IDs and native caller; query accepts only QueryInvocation. Account SID/session plus invocation UUID scopes idempotency. A same-lease retry returns the historical phase without replacing the original generation or issuing another ticket; another lease conflicts. Admission returns a queue hint only after commit. A worker needs a separately consumed fresh lease preflight, then a committed Queued-to-Running compare-and-set bound to service instance and a fresh nonce. Finishing matches the exact claim and cannot overwrite a terminal/recovered state. Recording VerifiedReenabled is the trusted worker's assertion after independent native observation; the ledger performs no such observation or effect.

Opening never automatically recovers, claims or replays work. Queued rows can be enumerated in batches of at most 64 for fresh owner review, including after lost ticket delivery. Only after external proof that an old owner stopped may the runtime mark that owner's Running rows Uncertain; these project RecoveryRequired and reject stale claim completion. The ledger itself cannot establish process death, singleton ownership or protected storage. Native effects must stay outside SQLite transactions, and any commit ambiguity must not trigger effect retry. Full runtime reconciliation, resource/lease authorization, protected storage provisioning, lifecycle/scheduling and retention remain open.

The owned connection must refer to a service-controlled file. The ledger rejects memory databases, attachments, temp objects, foreign/future/changed schemas and oversized data; it checks integrity before durability handling and again inside initialization. Schema v1 uses an exact STRICT WITHOUT ROWID table and fixed UUID/state constraints. DELETE journal mode is required without converting other modes; synchronous=EXTRA is set and verified. Busy waits are limited to 250 ms, database acceptance to 16 MiB, and retained invocations to 4,096. Capacity refuses new work while retaining old deduplication records; it does not prune receipts. A complete service needs its own long-term retention/admission strategy. SQLite's [transaction rules](https://www.sqlite.org/lang_transaction.html) and [synchronous settings](https://www.sqlite.org/pragma.html#pragma_synchronous) support this boundary; they do not prove storage hardware behavior or a hard wall-clock bound.

Eleven file-backed ledger fixtures exercise reopen/lost hints, scoped IDs, concurrent admissions/claims, injected statement and deferred-constraint commit failures, stale claims after recovery, stable terminal records, unknown/future/corrupt database preservation (including valid-header WAL/CHECK corruption), busy/read-only failures and bounded capacity/review. A separate Windows fixture carries actual pipe-authenticated frames through the admission/query boundary and checks command/ID mismatch rejection. These are transaction and API fixtures, not power-loss tests, a live service or native optimizer acceptance.

Custom Clean has a separate configured scan owner (`custom_clean`). Its private report retains exact file IDs, settings identity, eligible rule IDs and scan-time cutoffs; its serializable `Analysis` projection is display data marked `CleanupPolicy::CustomCleanRules`. The legacy age-only cleanup API rejects that policy before journaling. Configured cleanup resolves the whole selected-ID set, current saved-settings identity, partial-result acknowledgement and unsupported-effect constraints before the shared effect loop. That loop always checks root containment, link/reparse state and unchanged file metadata before the owner policy and system Trash call. Secure erase, folder-self removal, registry/cookie exclusions, free-space/ADS/MFT wiping, shutdown and close-process handling do not gain execution support from stored preferences.

The configuration dialog edits a draft and saves through the strict versioned settings store. Successful saving invalidates prior file results; scanning and cleaning load authoritative settings rather than treating the editor draft as authority. Exports retain the configured report, including omissions and per-rule eligibility. File and path exclusion matching is an explicit independent DCleaner policy; shipped request fields do not establish original native matching semantics. Built-in cache rules retain the existing minimum-age preference, while explicit inclusions use their own optional hour threshold. The 24-hour preference is limited to the supported built-in temporary-file rule. This preserves current behavior without claiming the original engine has been reproduced.

`DeferredJournal` opens no operation file until the first Start event, after preflight succeeds. Invalid settings, unsupported effects or stale IDs therefore do not leave empty operation files that would make History unreadable. Durable intent/outcome and uncertainty rules remain the same once an operation begins.

Configured scans share one matching-work budget across all file/path exclusions, folder filters and wildcard retries. Normalization/comparison work is charged and cancellation is checked inside matching. Work exhaustion stops scanning with an explicit truncated/partial report; unsupported matching input omits that candidate or subtree with a recorded reason. Neither condition is converted into a false exclusion match. Previously verified IDs remain reviewable only with partial-result acknowledgement; cancelled reports cannot authorize cleanup. Reports export the matching limit and usage, and the UI describes omissions in plain language. These are deterministic work units, not a wall-clock guarantee or evidence of original-engine equivalence.

Schema version 1 settings are replaced atomically through a same-directory temporary file. Per-operation JSON-lines journals record `start`, `intent`, `outcome`, `finish` with stable UUIDs. Each consequential journal entry is flushed and synced. Failure to preserve an intent prevents that file's Trash move. Failure after a move leaves an uncertain intent; no automatic retry follows restart. History is derived from journals and retains exact confirmed outcomes plus uncertainty. Invalid/truncated journals expose a recovery warning and preserve original bytes.

Windows stores DCleaner data in the user's local application-data directory. macOS uses `~/Library/Application Support/DCleaner`. Application replacement does not replace those directories. Source references, private path reports, credentials and user data stay out of Git. Exports are explicit native Save dialog actions.

## Capability boundaries

Baseline cleaning reads user-local temp/cache directories, skips links and recent/changed files, and uses system Trash. Registry changes, updates, secure erase, auto-emptying Trash and privileged locations need distinct typed services, explicit review/authorization and capability/recovery designs. 100% parity is a tracked acceptance target rather than a percentage inferred from menu count.

## Background verification and desktop boundary

The user requires confirmation before one inspection install and prohibits desktop/app/capture actions until then. Source work and background tests continue. Read-only WinGet inventory and the noninteractive pnputil export helper use `CREATE_NO_WINDOW`; the reviewed interactive update installer remains a separate explicit user operation.

The debug-only `src/offscreen_qa.rs` prepares CPU rasterization of the same egui tessellation, using `App::new_with_context` and `App::paint` without invoking eframe window creation or session-instance activation. It requires explicit isolated data/output paths, applies texture patches, clips and alpha blends meshes, rejects unsupported paint callbacks, and labels its output as software/layout evidence rather than a native framebuffer or installed acceptance. Pure rasterizer tests cover shared-edge blending/scissoring and bounded texture updates. Automatic approval review rejected execution of the app's offscreen entry point under the user's restriction; no offscreen app capture has run. Do not invoke it through an alternate harness/path to circumvent that rejection. Installed/GPU/interaction evidence remains separate and pending approval.
